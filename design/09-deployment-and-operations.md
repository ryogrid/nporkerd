# 09 — Deployment and Operations (Owner's Manual)

This document is for the project owner (Ryo). It lists **what you must do
yourself**, how every credential in the system is managed, and the exact
deployment procedure. Developers do not need a Convex account; only the
person deploying does.

## 1. The big picture

There is exactly one external service: **Convex**. You need:

- a Convex account (you log in; this account owns the project);
- two deployments of the same code: `dev` (for development) and `prod`
  (what players use);
- nothing else — no VPS, no DNS, no separate database, no object storage.
  The SPA is served by the deployment itself at
  `https://<prod-deployment>.convex.site`, and the API lives at
  `https://<prod-deployment>.convex.cloud`.

## 2. One-time setup (owner)

1. Create a Convex account at <https://www.convex.dev> (GitHub or Google
   sign-in). **Enable two-factor authentication on that identity provider.**
   This account is the root of the whole service.
2. On your machine: Node.js 20+ installed.
3. Clone this repository and install dependencies:
   ```bash
   git clone https://github.com/ryogrid/nporkerd.git
   cd nporkerd
   npm install
   ```
4. Link the project (creates the `dev` deployment and `.env.local`):
   ```bash
   npx convex dev
   ```
   Log in with the Convex account when prompted. This writes
   `CONVEX_DEPLOYMENT` into `.env.local` — that file is machine-local
   configuration, **gitignored, never commit it** (the repo's `.gitignore`
   already covers `.env.local`).
5. Create the production deployment: in the Convex dashboard, open the
   project → create a **Production** deployment (or let the first
   `npx convex deploy` create it). Note its URL
   (`https://<name>.convex.cloud`) — you will use it in §5.

## 3. Credential management (normative)

| # | Credential | Where it lives | Who may know it | Handling rules |
| --- | --- | --- | --- | --- |
| C1 | Convex account login (GitHub/Google) | Your identity provider + your password manager | You only | 2FA on. This account can do everything, including deleting the project. |
| C2 | **Deploy key** (production) | Convex dashboard → Project → Settings → Deploy Keys | You only; a CI secret store if CI is ever added | Treat as a root password. Store it in your password manager (e.g. 1Password). **Never** put it in the repo, in chat, or in the SPA. If it leaks: dashboard → revoke immediately, generate a new one. Local deploys from your logged-in CLI session do not need the key at all — the key exists for non-interactive/CI deploys (`CONVEX_DEPLOY_KEY` env var). |
| C3 | `CONVEX_DEPLOYMENT` in `.env.local` | Your dev machine only | Developers with repo access | Not a secret per se (it names the dev deployment), but keep `.env.local` out of git as a matter of hygiene. It is regenerated by `npx convex dev`. |
| C4 | `VITE_CONVEX_URL` | Baked into the public SPA at build time | Everyone (it is public) | **Not a credential.** It is the deployment's public API URL; every visitor's browser needs it. Dev builds point at dev, prod builds at prod — mix-ups here are the #1 deployment mistake (SPA talking to the dev backend). The static-hosting deploy command sets it for you when using its `--build` flow; if you build manually, set it explicitly (§5). |
| C5 | Users' private keys (`npk_…`) | Each user's own keeping | That user only | **You never see, store, or can reset these.** They are generated in the user's browser and never transmitted. If a user loses theirs: the account is gone; tell them to register a new username. There is no admin override to build — do not ask a developer to add one; it would defeat the design (R4). |
| C6 | Database credentials | — | — | **None exist.** Convex data is accessible only through deployed functions, the dashboard (C1), or the CLI/deploy key (C2). There is no connection string to leak. |

Environment variables on a deployment (`npx convex env set NAME value` or
dashboard → Settings → Environment Variables): **v1 needs none.** If a
future feature adds one (e.g. an external API key), it is set per-deployment
in the dashboard, never committed, and listed here by name (never by value).

## 4. Development workflow (for whoever implements)

```bash
npx convex dev        # terminal 1: syncs convex/ functions to the DEV deployment, runs codegen
npm run dev           # terminal 2: Vite dev server for the SPA (uses dev deployment URL from .env.local)
```

- All development happens against the **dev** deployment. Its data is
  throwaway.
- `npx convex dev` regenerates `convex/_generated/` — commit those files.
- Reset dev data any time from the dashboard (Data → clear) or by deleting
  documents in the data browser.

## 5. Production deployment procedure

Prerequisites: §2 done; code merged to `main`; tests green
(`npm test`).

1. **Back up production data** (optional but recommended before schema
   changes):
   ```bash
   npx convex export --prod --path ./backup-$(date +%F).zip
   ```
2. **Deploy the backend** (functions + schema to the prod deployment):
   ```bash
   npx convex deploy
   ```
   (`--prod` is the default target of `deploy`; from a non-interactive
   shell, set `CONVEX_DEPLOY_KEY=<prod deploy key>` instead of being
   logged in.)
3. **Build and upload the SPA** using the static-hosting component's CLI
   from the repo root. Its one-command flow builds the app with the correct
   `VITE_CONVEX_URL` for the target deployment and uploads the assets:
   ```bash
   npx @convex-dev/static-hosting deploy --build --prod
   ```
   *Verify the exact subcommand/flags against the installed package version
   (`npx @convex-dev/static-hosting --help`) — the component is young
   (0.2.x) and its CLI surface may move. The invariant that matters: the
   build must embed the **prod** `*.convex.cloud` URL, and the upload must
   target the **prod** deployment.*
4. **Smoke test** on `https://<prod-deployment>.convex.site`:
   - [ ] Page loads; no console errors; the site talks to prod (register a
     throwaway user and confirm it appears in the **prod** dashboard's
     `users` table, not dev's).
   - [ ] Register → key reveal → download works; logout; login with the
     downloaded key works.
   - [ ] Create a room; in a second browser/profile, register a second
     user, join, sit down.
   - [ ] Host starts the game; a hand plays to completion (use short turn
     timers); chat messages cross between the two browsers.
   - [ ] Reload mid-hand: the table state is restored from the server.
5. Note the release in the repo (tag or changelog entry) with the date and
   the prod deployment name.

Rollback: redeploy the previous commit (`git checkout <prev> && npx convex
deploy` + SPA upload). Schema changes are the risky part: Convex validates
deployed functions against the schema; follow Convex's schema-migration
guidance and prefer additive changes (new optional fields) so a rollback
never strands data.

## 6. Routine operations

| Task | How | Cadence |
| --- | --- | --- |
| Check usage / limits | Dashboard → project → Usage. Reactive game traffic consumes function calls on every state change for every subscribed client — a busy table is the main cost driver. Check the current plan's included amounts in the dashboard. | Monthly, and after any traffic spike |
| Look at / fix data | Dashboard → Data browser (prod). You can see everything, including `hands` documents — remember players cannot; don't paste raw hand documents anywhere public mid-game. | As needed |
| Run a function manually | Dashboard → Functions → run, or `npx convex run --prod <fn> '<json>'` | As needed |
| Backup | `npx convex export --prod` (see §5.1) | Before deploys; monthly otherwise |
| A user lost their key | Nothing to do — impossible by design (C5). Offer a new registration. | — |
| Suspected deploy-key leak | Revoke in dashboard → Deploy Keys; issue a new key; update the CI secret if any; then redeploy once to confirm. | Immediately |
| Abuse in a room | No admin tooling in v1. Hosts close rooms. If server-level action is unavoidable, the owner can edit/delete documents via the Data browser. | — |

## 7. Plan limits to be aware of

Convex's free tier is sized for prototypes; the exact quotas (function
calls, database bandwidth/storage, file storage/bandwidth for the SPA)
change over time — check the dashboard's Usage page and Convex's pricing
page when you set up, and again before inviting a larger group. Design
assumption for v1: a handful of simultaneous tables among friends. If usage
approaches a quota, the remedies in order are: upgrade the Convex plan (a
dashboard action, no code change), then optimise the chattiest queries
(`getTableState` projections) if still needed.
